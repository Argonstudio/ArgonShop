# AI_VERSIONING.md — версии проекта

Продолжение [AI.md](../../AI.md).

## 1. Текущий релиз и источник версии

Плагин и тема выпускаются вместе с номером **1.1.0**. Номер релиза задаётся ровно в трёх местах:

| Файл | Поле |
|---|---|
| `plugins/argon-shop/argon-shop.php` | заголовок `Version:` |
| `plugins/argon-shop/argon-shop.php` | `ARGON_SHOP_VERSION` |
| `themes/argon-shop-theme/style.css` | заголовок `Version:` |

Все три значения должны совпадать. `AI.md` и заголовки `Project-Id-Version` в `.pot` / `.po` должны описывать тот же релиз; после изменения `.po` пересоберите `.mo`.

Версия также меняет URL CSS/JS для обновления кэша. Static-check проверяет совпадение версий и наличие раздела этой версии в журнале изменений. Не добавляйте отдельные `@version` в файлы.

## 2. Выбор следующего релиза

Номер релиза согласуется с мейнтейнером явно; не назначайте будущую минорную версию автоматически при добавлении помощника.

- Исправление без несовместимого изменения API: повысить patch (`X.Y.Z` → `X.Y.(Z+1)`).
- Совместимая новая возможность: повысить minor (`X.Y.Z` → `X.(Y+1).0`).
- Несовместимое изменение: повысить major (`X.Y.Z` → `(X+1).0.0`).

При нескольких изменениях действует самое крупное. `Requires PHP` и `Requires at least` — требования к окружению, а не версия ArgonShop.

## 3. Работа и выпуск

Для невыпущенных изменений добавляйте запись в `[Unreleased]` и не меняйте номер без явной просьбы о релизе.

При выпуске:

1. Согласуйте целевой номер.
2. Обновите три поля выше, документацию о текущей версии и заголовки переводов; пересоберите `.mo`.
3. Соберите изменения релиза в одном разделе `## [X.Y.Z]`, оставив пустой `[Unreleased]` сверху.
4. Добавьте необходимые миграции и инструкции обновления; не меняйте контракты данных без миграции.
5. Выполните `php tests/static-check.php`, `php tests/regression-check.php`, `node tests/number-check.mjs` и на тестовом сайте `wp eval-file tests/smoke-test.php`.

## 4. Отметки функций и хуков

`@since` обозначает релиз появления функции/хука или описанного поведения. Возможности текущего релиза получают `@since 1.1.0`. Для следующих изменений используйте номер, явно согласованный с мейнтейнером, а не придуманную будущую версию. После публикации релиза эти отметки не переписываются.

Сохраняйте обёртки совместимости публичного API и их `@deprecated` в `includes/legacy-functions.php`.

## 5. Миграции данных

Версия данных хранится в опции WordPress `argon_shop_version` и не равна комментарию в коде. `as_maybe_upgrade()` в `includes/install.php` сравнивает её с `ARGON_SHOP_VERSION`.

Текущая миграция имеет ключ `1.1.0` и колбэк `as_migrate_1_1_0`. Сохраните оба: при переходе с 1.0.0 на 1.1.0 должна выполняться очистка старых публичных файлов заказов. Не сбрасывайте опции БД и не переименовывайте миграции только ради правки документации.

Следующие миграции должны быть идемпотентными и включаться в `as_get_migrations()` под согласованным номером релиза. Изменения мета/cookie/опций требуют миграции; правка номера релиза не откатывает данные.

## 6. Сторонний код и дополнения

Исходные версии форков в `breadcrumbs.php`, `pagenavi.php`, `last_viewed_posts.php`, версии библиотек vendor и лицензий не являются версиями ArgonShop. Сохраняйте их. Изменения стороннего кода описываются в журнале проекта без отдельных версий файлов.

Модули внутри репозитория имеют общую версию проекта. Отдельный номер, заголовок плагина, журнал и требование к ArgonShop получает только независимо выпускаемое дополнение.
